How NIR Analyzers Integrate with PLC and SCADA Systems: A Practical Overview

Which protocols carry a near-infrared analyzer’s results into the plant control system, what a result record must contain before a PLC may act on it, where latency comes from, and how alarms, historians and cybersecurity are handled — with the governing standards and literature.

Where the analyzer sits in the automation hierarchy

An inline NIR analyzer produces composition values that are useful for control only if they reach the systems that act on them. IEC 62264-1 (ISA-95) describes this interface in levels: Levels 1 to 3 form the manufacturing operations and control domain, Level 3 is manufacturing operations management, and Level 4 is the enterprise domain [1]. The FDA’s PAT guidance notes that process analyzers typically generate large volumes of data, that easy and secure access to them is important for real-time control and quality assurance, and that measured quality attributes can drive feed-forward or feed-back control [2]. This matters in the chemical and pharmaceutical industries and beyond; closed-loop PID dosing is covered in a separate guide.

Protocols: from the current loop to OPC UA

The oldest path is the analogue direct-current signal of IEC 60381-1 [3], with 4–20 mA specified as the signalling range by ISA-50.00.01 [4]. Every PLC accepts it, but a multi-parameter analyzer needs one loop per parameter, and the signal carries no status word or timestamp. Modbus is a request/reply client/server protocol whose server exposes discrete inputs, coils, input registers and holding registers, the registers being 16-bit words; on TCP/IP it uses port 502 [5]. A floating-point result therefore spans more than one register, and since the specification defines no timestamp or quality field, status must be mapped into further registers by the integrator [5].

EtherNet/IP and PROFINET are cyclic real-time Ethernet systems, belonging in the IEC profile standards to Communication Profile Family 2 (CIP) and Family 3 (PROFIBUS & PROFINET) [6][7]; they suit an analyzer that must appear as an I/O device in the controller scan. OPC UA (IEC 62541) is a platform-independent standard whose servers expose an address space of typed nodes, with services for reading, writing and subscribing to data changes, events and alarms, and with authentication and message integrity and confidentiality built in [8]. It is the usual path to SCADA, MES and historians.

The result record: value, status, timestamp

A result is safe to act on only if it carries three things. OPC UA formalises them as the DataValue: the value, a StatusCode of severity Good, Uncertain or Bad, and a SourceTimestamp set by the originating source and passed through unchanged by intermediate servers [9]. The status says whether the PLC may use the number; the timestamp says when the material was measured.

For device health, NAMUR NE 107 describes standardised status signals, their symbols and their prioritisation [10]: failure, function check, out of specification and maintenance required [11]. They must be exposed as a status word beside each value: with Modbus that mapping must be designed [5]; with OPC UA the StatusCode exists but the analyzer software must set it [9].

Latency: measurement, sampling and publishing

Latency is the sum of spectral acquisition, model evaluation and communication. In OPC UA the communication part is set by the sampling interval at which the server checks the source and the publishing interval at which notifications are delivered; the specification notes that an unsynchronised, slower update cycle of the source adds further delay [9]. In Modbus the equivalent is the client’s polling period [5]. Analyzer values thus arrive late and at variable intervals; Griesing-Scheiwe et al. show that estimators assuming constant delay and sampling time can become unstable when these vary [12]. Three practice points follow:

  • Align polling or publishing with the analyzer cycle. Reading faster than the analyzer produces results only re-reads the same value; the source timestamp, not the poll, identifies a new measurement [9].
  • Transport status with every value. The PLC should hold its last good value or fall back to a defined mode when the status is Bad or Uncertain, or when the device reports failure [9][11].
  • Document scaling, units and data types. Modbus registers carry none of these, so the interface specification must [5].

Alarms, historians and cybersecurity

IEC 62682 sets out principles for managing process-industry alarm systems, counts the alarm historian and performance metrics as part of the alarm system, and defines its purpose as notifying operators of abnormal conditions that need a response [13]. Analyzer composition limits should therefore be rationalised with the plant’s other alarms, and results should be stored with status and timestamp in the plant historian, consistent with the Level 3 functions of ISA-95 [1] and the PAT guidance on batch records [2].

On the network, IEC 62443-3-3 defines system security requirements and security levels, applied through the zones and conduits of the system to set a target level for each asset [14]. An analyzer in its own zone, with a conduit carrying only the agreed tags, follows that model; OPC UA supports it with application and user authentication and signed, encrypted messages [8].
